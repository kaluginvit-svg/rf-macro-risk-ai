# Методика перекалибровки критериев

Цель перекалибровки — превратить набор критериев из описательного списка в проверяемую систему раннего предупреждения. Модель должна искать и объяснять факты, а итоговые баллы, пороги, повторное использование источников и статусы критериев должны считаться кодом.

## 1. Разделение критериев по роли

Каждый критерий должен иметь роль. Это помогает задавать вес, глубину ресерча и требования к источникам.

### `shock`

Редкие аварийные события:

- банковские каникулы;
- реструктуризация или принудительный обмен ОФЗ;
- остановка торгов;
- внеплановое экстренное повышение ставки;
- крупная санация или временная администрация системного банка;
- форс-мажорное государственное событие.

Правила:

- высокий вес;
- почти всегда `official-only`;
- срабатывание возможно только по официальному источнику или официальному сообщению, перепечатанному надежным СМИ;
- один такой критерий может резко поднять итоговый риск.

### `leading`

Ранние признаки ухудшения:

- рост РЕПО;
- рост M0;
- спред ставок по вкладам;
- cash-FX premium;
- корпоративные дефолты;
- NPL;
- просрочка населения;
- стресс ипотеки;
- спрос на ОФЗ;
- межбанковская ликвидность.

Правила:

- средний вес;
- важна динамика, а не единичная новость;
- желательно 2 независимых подтверждения, если источник не официальный;
- критерий может иметь частичные статусы `watch` и `warming_up`.

### `context`

Фоновые макроиндикаторы:

- инфляция;
- инфляционные ожидания;
- внешняя торговля;
- РЖД;
- розница;
- промпроизводство;
- региональные бюджеты;
- рынок труда.

Правила:

- низкий или средний вес;
- не должен один переводить систему в красную зону;
- лучше использовать официальную статистику;
- горизонт анализа может быть длиннее, чем у `shock` и `leading`.

## 2. Формальная триггерная формула

У каждого критерия должна быть не только текстовая интерпретация, но и формальное правило.

Минимальные поля:

```json
{
  "id": "corporate_default_wave",
  "role": "leading",
  "metric": "defaults_count_30d",
  "trigger": ">= 10 corporate defaults OR >= 3 sectors affected",
  "window_days": 30,
  "baseline": "previous 12 months monthly average",
  "weight": 8,
  "cooldown_days": 14,
  "min_sources": 2
}
```

Рекомендуемые поля:

- `metric` — что измеряем;
- `trigger` — точное условие срабатывания;
- `window_days` — временной горизонт;
- `fallback_window_days` — допустимый запасной горизонт;
- `baseline` — с чем сравниваем;
- `source_policy` — какие источники допустимы;
- `cooldown_days` — сколько дней событие не должно повторно давать полный вес;
- `severity_levels` — уровни частичного срабатывания.

## 3. Небинарные статусы

Текущая схема `triggered / not triggered` слишком грубая. Лучше использовать уровни:

| Статус | Вес | Значение |
| --- | ---: | --- |
| `quiet` | 0% | свежих признаков нет |
| `watch` | 25% | слабый сигнал, нужен мониторинг |
| `warming_up` | 50% | сигнал усиливается, но порог не пройден |
| `triggered` | 100% | критерий сработал |
| `critical` | 150% | аварийное событие или резкое ухудшение |

Пример:

```json
{
  "id": "household_credit_stress",
  "weight": 5,
  "severity_levels": {
    "watch": "retail_npl_yoy > 10%",
    "warming_up": "retail_npl_yoy > 20%",
    "triggered": "retail_npl_yoy > 30% OR npl_share_90d reaches 5y high",
    "critical": "retail_npl_yoy > 50% AND credit issuance collapses"
  }
}
```

## 4. Сценарная модель весов

Веса нужно пересчитывать не от эмоционального восприятия критерия, а от вклада в целевые сценарии.

Базовые сценарии:

1. доступ к вкладам и платежам;
2. банковский стресс;
3. бюджетный стресс;
4. валютно-платежный стресс;
5. корпоративный кредитный стресс;
6. спад реальной экономики;
7. инфляционно-ставочный стресс.

Каждый критерий должен иметь вклад в один или несколько сценариев.

Пример:

```json
{
  "id": "payment_infrastructure_systemic_disruption",
  "scenario_weights": {
    "deposit_access": 0.45,
    "banking_stress": 0.25,
    "trade_finance": 0.15,
    "general_crisis": 0.15
  }
}
```

## 5. Два отдельных скоринга

Нужно разделить общий риск и риск доступа к деньгам.

### `crisis_score_6m`

Общий риск кризисного сценария на горизонте 6 месяцев.

Использует все критерии, но с учетом роли и статуса:

```text
crisis_score_6m =
  sum(weight * severity_multiplier * freshness_multiplier * novelty_multiplier)
```

### `deposit_access_score_1_3m`

Отдельный риск доступа к вкладам, платежам и ликвидности.

Пример формулы:

```text
deposit_access_score =
  bank_holidays_national * 40
  + payment_infrastructure_systemic_disruption * 20
  + systemic_bank_resolution * 20
  + interbank_liquidity_stress * 10
  + deposit_outflow_mass * 10
```

Остальные критерии могут влиять только косвенно и с малым коэффициентом.

## 6. Новые пороги риска

Текущие пороги `0–12`, `13–26`, `27+` слишком чувствительны: несколько средних критериев сразу дают красную зону.

Рекомендуемая 4-зонная шкала:

| Зона | Очки | Значение |
| --- | ---: | --- |
| `green` | 0–19 | стабильный фон |
| `yellow` | 20–39 | повышенное внимание |
| `orange` | 40–69 | существенный стресс |
| `red` | 70+ | высокий системный риск |
| `black` | official shock | аварийный режим |

Если нужна только 3-цветная шкала:

| Зона | Очки |
| --- | ---: |
| `green` | 0–19 |
| `yellow` | 20–49 |
| `red` | 50+ |

Важно: `black` не должен зависеть от суммы баллов. Это отдельный флаг для аварийных official-only событий.

## 7. Anti-repeat и новизна

Критерий не должен каждый прогон давать полный вес за одну и ту же старую историю.

Правила:

- если событие уже учтено и новых данных нет: `novelty_multiplier = 0`;
- если появились новые данные по той же теме: `novelty_multiplier = 0.25–0.50`;
- если появился новый независимый эпизод: `novelty_multiplier = 1.00`;
- если событие стало системным или резко ухудшилось: `novelty_multiplier = 1.00–1.50`.

Для этого нужен `research_ledger.json` или аналогичный журнал:

```json
{
  "event_key": "corporate_defaults_2026w21",
  "criteria_id": "corporate_default_wave",
  "first_seen": "2026-05-22",
  "last_seen": "2026-05-23",
  "source_urls": ["https://..."],
  "score_applied": 8,
  "cooldown_until": "2026-06-06"
}
```

## 8. Freshness по типам критериев

Горизонт свежести должен зависеть от типа критерия.

| Тип | Основной горизонт | Fallback | Комментарий |
| --- | ---: | ---: | --- |
| `fast` | 1–7 дней | 30 дней | события, решения, сбои |
| `medium` | 30 дней | 45 дней | кредит, санкции, рынки, дефолты |
| `slow` | последний официальный релиз | 120 дней | статистика с задержкой |

Для `slow`-критериев важна не дата статьи, а дата релиза официальной статистики.

## 9. Источники и группы критериев

### `official_event`

Примеры:

- `cbr.ru`;
- `minfin.gov.ru`;
- `kremlin.ru`;
- `government.ru`;
- `rg.ru`;
- `moex.com`.

Правила:

- для shock-критериев обязательны;
- неофициальные источники не могут сами включать критерий;
- официальные источники можно переиспользовать в разных критериях.

### `official_stats`

Примеры:

- `rosstat.gov.ru`;
- `cbr.ru`;
- `fedresurs.ru`;
- `rzd.ru`;
- `minfin.gov.ru`.

Правила:

- приоритет официальным временным рядам;
- СМИ можно использовать как навигацию, но не как единственное основание, если доступен официальный релиз.

### `news_event`

Примеры:

- `rbc.ru`;
- `kommersant.ru`;
- `vedomosti.ru`;
- `interfax.ru`;
- `tass.ru`;
- `banki.ru`.

Правила:

- минимум 2 независимых источника, если нет официального подтверждения;
- один и тот же источник не должен закрывать несколько независимых критериев, кроме официальных данных;
- старые и недатированные материалы не считаются.

### `market_data`

Примеры:

- `moex.com`;
- `cbr.ru`;
- `minfin.gov.ru`;
- биржевые и долговые агрегаторы.

Правила:

- желательно использовать временной ряд, а не одну публикацию;
- одно дневное движение не должно включать критерий без продолжения.

## 10. Историческая калибровка

Нужно прогнать систему по контрольным периодам:

- февраль–март 2022;
- сентябрь–октябрь 2022;
- июнь 2023;
- декабрь 2023;
- спокойные периоды 2024–2025;
- текущий 2026.

Цели:

- в феврале–марте 2022 система должна давать `red` или `black`;
- в спокойные периоды система не должна постоянно быть `red`;
- isolated news shock не должен раздувать общий риск без подтверждений;
- повтор старой темы не должен давать полный вес.

## 11. Отчет по качеству каждого прогона

После каждого прогона нужно сохранять:

- сколько критериев проверено;
- сколько источников принято;
- сколько источников отклонено;
- сколько критериев сработало впервые;
- сколько критериев повторилось;
- какие критерии дали основной вклад;
- confidence по группам;
- список `quiet/watch/triggered`;
- причины отклонения старых или слабых источников.

Минимальный формат:

```json
{
  "run_id": 12,
  "checked_criteria": 35,
  "accepted_sources": 58,
  "rejected_sources": 21,
  "triggered": 8,
  "watch": 6,
  "quiet": 21,
  "top_contributors": [
    "payment_infrastructure_systemic_disruption",
    "corporate_default_wave",
    "budget_emergency_amendments"
  ]
}
```

Перенести математику из промпта в код:

Роль модели:

- искать;
- читать;
- извлекать факты;
- объяснять, почему критерий сработал или не сработал.

Роль кода:

- считать;
- валидировать;
- дедуплицировать;
- применять пороги;
- сохранять журнал;
- формировать машинно-проверяемый результат.
